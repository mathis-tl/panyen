DESTINATAIRE — nouveau Cursor Agent

OBJECTIF UTILISATEUR
À chaque push sur `main` et chaque pull request, prouver automatiquement qu’un
clone propre peut installer les dépendances verrouillées puis vérifier toute la
tranche alimentaire : lint Python, tests Python, modèles/tests dbt, tests web et
build statique. Une erreur doit bloquer la CI avec une sortie lisible.

DÉCISION SUR LE « DRY-RUN REPRODUCTIBLE »
La CI de pull request ne contacte pas l’API Insee. Le collecteur
`ingest/insee_ipc.py --dry-run` réalise une vraie requête réseau avant de ne rien
écrire : l’exécuter dans le job bloquant rendrait les PR dépendantes d’un service
externe.

Le contrat reproductible est le test existant
`tests/test_insee_ipc.py::test_dry_run_n_ecrit_rien`, avec réponse synthétique :
le chemin dry-run est exécuté sans réseau et prouve qu’il n’écrit aucun brut. Le
smoke test live et la collecte planifiée restent en incrément 5.

SOLUTION MAINTENUE RETENUE
Un seul workflow GitHub Actions et les actions officielles/maintenues, sans
infrastructure maison :
- `actions/checkout`, `actions/setup-python`, `actions/setup-node` ;
- `astral-sh/setup-uv`, recommandé par la documentation officielle uv ;
- toutes les actions tierces épinglées sur un SHA complet de 40 caractères, avec
  le tag stable correspondant en commentaire.

CONTRAT DE LA COMMANDE LOCALE
- Ajouter une cible `make ci` qui appelle l’installation verrouillée existante,
  puis `make verify`, sans dupliquer les commandes de vérification.
- `make ci` est le contrat unique appelé par GitHub Actions et reproductible
  localement.
- Ajouter `ci` à `.PHONY`.
- Ne pas affaiblir `make verify`, `make publier` ni leurs ordres d’exécution.
- La cible `ci` exécute la vérification avec `UV_LOCKED=1` afin que ses `uv run`
  refusent de modifier `uv.lock`, localement comme dans GitHub Actions.

CONTRAT DU WORKFLOW
- Créer uniquement `.github/workflows/ci.yml`, avec un nom explicite.
- Déclencheurs : `pull_request`, push sur `main` et `workflow_dispatch`.
- Permissions minimales au niveau workflow : `contents: read`.
- Un seul job `verification`, sur `ubuntu-24.04`, avec
  `timeout-minutes: 15`.
- Ajouter une concurrence par workflow et référence, avec annulation de l’ancienne
  exécution pour une même branche/PR.
- Étapes, dans cet ordre :
  1. checkout ;
  2. Python depuis `.python-version` ;
  3. uv maintenu, version binaire explicitement fixée à `0.12.7`, cache uv fondé
     sur `uv.lock` ;
  4. Node `24.9.0`, cache npm fondé sur `web/package-lock.json` ;
  5. `make ci`.
- Utiliser les SHA complets ci-dessus et garder le tag en commentaire.
- Ne transmettre aucun secret et ne demander aucune permission d’écriture.
- Ne lancer ni collecte live, ni `make publier`, ni déploiement.

CONTRAT DE REPRODUCTIBILITÉ
- Ajouter `.node-version` contenant exactement `24.9.0` et demander à
  `setup-node` de le lire ; ne dupliquer la version dans le YAML que si l’action
  ne sait pas lire ce fichier.
- `uv sync --locked` et `npm ci` restent les seules installations.
- Aucun lockfile ne doit changer pendant `make ci`.
- Le workflow doit utiliser le brut Insee déjà versionné ; il ne télécharge aucune
  donnée métier.
- Après `make ci`, vérifier que `data/raw/insee/` n’a subi aucune modification.
- Les caches ne contiennent aucun secret ni résultat métier. Ils sont des
  optimisations : une absence de cache ne doit pas changer le résultat.
